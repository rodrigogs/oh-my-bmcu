# Firmware audit — September 2026

Audit of the V10.5 sources (plus upstream PR #134) run on 2026-09-23 for **oh-my-bmcu**, targeting one BMCU 370C on a Bambu Lab A1 (printer firmware 01.08.01.00, `standard(A1)`, SOLO 0.095 m, AUTOLOAD, RGB off).

Method: four independent investigators (bus/timing, motion/sensors, persistence, upstream issues + tooling), each followed by an adversarial reviewer that re-read the cited code and tried to refute every finding, then a completeness critic. Only code-backed findings with a concrete failure scenario were kept. Verdicts: `confirmed` = the reviewer found the defect in the code; `plausible` = reachable but unproven; `critic-only` = reported by the critic and not re-reviewed. Duplicates found by more than one investigator are merged below. Line numbers refer to commit `73497e9`.

Nothing here has been tested on hardware yet unless the status says so. "A1" = relevance to our setup.

## Findings

<a id="ws2812-always-dirty-irq-off-redraw"></a>
### 1. Active-channel LED strip is redrawn every loop during a print (baseline/state color flip-flop); each redraw disables IRQs ~59 us and drops USART1 RX bytes

- **id:** `ws2812-always-dirty-irq-off-redraw`
- **kind / severity / A1:** bug / high / direct
- **verdict:** confirmed
- **status:** fixed on `main` (`a08c7de`: redraw only when the shown colours change); hardware validation pending
- **location:** src/ws2812.cpp:142-151, src/ws2812.cpp:103-140, src/Motion_control.cpp:2384-2408, src/Motion_control.cpp:2513-2521, src/Motion_control.cpp:2346, src/main.cpp:20-23, src/main.cpp:26-49
- **related:** upstream #134/#104/#97 (root cause of the 1 kHz redraw); may contribute to #126, #141

**Failure scenario.** A1 printing from slot N (motion on_use): RGBOUT[N] is rewritten every 10 ms. Any printer frame that overlaps the 58.7 us window loses about 5-6 bytes (USART overrun: single-byte DATAR, no FIFO). Chance per frame is about (T_frame + 59 us) / 10 ms: ~1.6% for a 12-byte 0x03 motion poll, ~4-5% for a 40-60 byte frame. Before PR #134 (every ~1 ms loop) it was tens of percent, which matches the lost set_filament_info. Because of the no-resync issue (separate finding), each hit also usually kills the next frame. Our reply TX is DMA and survives, but the TC ISR that releases DE can also be held up to ~59 us.

**Suggested fix.** Fix the root cause in WS2812_class: add `uint32_t shown_grb[MAX_NUM]`. In updata(), return early unless some last_grb[i] != shown_grb[i], and copy last_grb to shown_grb after writing. Keep is_dirty() consistent with that. Alternatively, have Motion_control compute one final color per channel per loop and call MC_STU_RGB_set once. With that, a steady on_use state causes zero redraws. Defense in depth: (a) move USART1 RX to circular DMA (DMA1_Channel5 is free: ADC uses Ch1, debug Ch2, TX Ch4) so IRQ-off windows can no longer drop RX bytes; and/or (b) re-enable IRQs during each bit's low phase or per nibble (the fast ISR is ~83 instructions, and WS2812 tolerates a TL stretch of a few us); and/or (c) only redraw when the bus is quiet (TX idle, parser at idx 0, and >= N us since the last RX byte).

**Review.** Verified in code. set_RGB (ws2812.cpp:147-150) compares against last_grb, which is the last requested value, not the last shown one. Every pass, stu_apply_baseline (Motion_control.cpp:2513, DM branch 2407-2408) writes white or black into RGBOUT[i] LED0. motor_motion_switch (2522) then writes the state color for the active channel: on_use 0x00B0FF at 2346, before_on_use 2232, stop_on_use 2240, send_out 2262, pull_back 2270. The value flips every pass, so dirty is always true when RGB_update runs (main.cpp:28-48). updata() keeps IRQs off (irq_save_wch clears MIE/MPIE in CSR 0x800) for 2 LEDs x 24 bits x 22 ticks = 1056 ticks at 18 MHz, about 58.7 us. The UART runs 1.25 Mbaud 9E1 (11 bits, 8.8 us per byte) with single-byte DATAR, so about 5-6 bytes overrun. The 10 ms throttle only caps this at 100 redraws/s. It also hits our A1 when the printer is idle, not only while printing. on_use is sticky while filament sits in the toolhead: set_motion ignores idle/other commands when motion is on_use/before/stop_on_use (bambu_bus_ams.cpp:401-405), and main.cpp:216 restores on_use from the flash state at boot. So a unit with one channel loaded redraws a strip continuously, including while the user edits slots (the #134/#104/#97 symptom).

**Review corrections.** Line numbers are correct. More context: the 100 Hz redraw is continuous whenever a channel is loaded, not only during motion. The online LED (index 1, Motion_control.cpp:2725) is compare-guarded and does not flip-flop by itself. Fix notes: with the shown_grb approach, also make is_dirty() return (last_grb != shown_grb) so RGB_update's gate stays consistent. A cheaper alternative with the same effect: have stu_apply_baseline skip the channel that motor_motion_switch will override, or build a per-channel color array and call MC_STU_RGB_set once per pass. Moving RX to circular DMA on DMA1_Channel5 (USART1_RX) is a good extra safeguard.

<a id="jam-latch-single-sample-sticky"></a>
### 2. On-use jam/tangle latch has no time qualification (a few ms below 40% buffer trips it) and a printer resume cannot clear it

- **id:** `jam-latch-single-sample-sticky` (merged: `jam-latch-single-sample-no-recovery`)
- **kind / severity / A1:** bug / high / direct
- **verdict:** confirmed
- **status:** open
- **location:** src/Motion_control.cpp:1894-1908, 1025-1034, 788-793, 2244-2260, 2355-2360, 2757-2761, 2771-2777
- **related:** #127, #139 (possibly part of #125)

**Failure scenario.** A1 printing, on_use. The spool snags briefly (heavy spool, dryer-box feed, loose wrap). The extruder drains the buffer below 40% for ~5 ms. The BMCU latches: motor braked (PWM 0 = both outputs high), LED red, pressure 0xF06F, so the A1 pauses with a tangle error. The user clears the snag and presses resume. The printer re-sends on_use, the latch is still set, 0xF06F goes out again and the print pauses right away. It recovers only after pulling the filament out past both switches or power-cycling. This matches #127 ('resumed then paused again', 'removed filament fully... after putting it back it recognized it', 'reboot fixes it') and #139 ('need to remove all filament and feed it again, because the bmcu turn on the red led').

**Suggested fix.** (1) Time-qualify the trip. Require pct < 40 continuously for about 0.5-1.5 s while the controller is commanding at least ~800 PWM push AND |speed_as5600| is ~0 (real stall), or use a count of consecutive samples. Ignore the first ~1 s after entering on_use from stop_on_use/idle. (2) Make it recoverable. Clear jam_latch when the printer re-issues before_on_use/on_use after any non-on_use motion (the resume path), or after the buffer has been back above MC_ON_USE_TARGET_PCT for about 1 s. Optionally allow one automatic retry before reporting. (3) For the 20 s high-PWM latch, report it (0xF06F) or release it when pct recovers instead of braking silently.

**Review.** The code matches the finding. Trip at Motion_control.cpp:1894-1908: `if (pct < 40.0f) { g_on_use_low_latch = 1; g_on_use_jam_latch = 1; }`. There is no timer, no check that a push is being commanded, and no AS5600 stall check. Once latched, run() returns at 1025-1034 with Motion_control_set_PWM(CHx,0). That sets both compares to 1000 (above ARR 999), so both outputs are high: the H-bridge brakes, it is not freewheeling. Motion_control_run (2771-2777) forces A.pressure=0xF06F while the printer-side motion is on_use or send_out. The bus handler keeps it (bambu_bus_ams.cpp:327 `if (pressure != 0xF06F) pressure = 0x2B00`). The only places that clear jam_latch are set_motion (788-793, blocked by `!g_on_use_jam_latch`), send_out with pct>85 (2246-2251) and ks==0 (2757-2760). Idle keeps the motor stopped (2276/2355). A pull_back with the latch set retracts a fixed 100 mm (2276-2279) and does not clear it. So a resume that re-sends on_use gets 0xF06F again straight away. This contradicts README V9/V10 ('lock released when buffer returns to neutral', 'resume normally'). The symptoms in #127 match: 'impossible to return printing', 'filament was retracted a bit', 'push filament to extruder... started to feed... paused again' (manually pushing the buffer above 85% during send_out is the hidden unlatch path). #139 also matches: 'remove all filament and feed it again... red LED', which is the ks==0 clear. The 20 s high-PWM sub-claim also holds (1919-1931). It sets low_latch with jam=0, which brakes the motor silently for the rest of on_use and disables the <40% check (the 1894 guard is `!g_on_use_low_latch`).

**Review corrections.** (1) It is not a single raw sample. MC_PULL_pct_f comes from the ADC 4-block moving average (window about 4.8 ms, refreshed about every 1.2 ms), so the filtered value must stay below 40% for a few ms. Mechanically this is still effectively instant. (2) The sub-claim that it 'fires on first run() after entering on_use from stop_on_use' needs the buffer to already be below 40% at entry. That is not shown, so treat it as speculative. The stop_on_use brake is at 1487-1494, not '1034-1494'. (3) There is an undocumented escape: while the printer is in send_out, pushing the buffer above 85% clears the latch (2246-2251). (4) During either latch the motor is actively braked, not freewheeling, so the extruder pulls against a braked gear. Better fix: time-qualify the trip (for example 300-1000 ms below 40% with push PWM of at least 800 and |speed| near 0). Clear jam_latch once the printer has acknowledged the error, i.e. on the next transition out of on_use (stop_on_use/before_on_use/idle issued after the latch) or when pct stays at or above MC_ON_USE_TARGET_PCT for about 1 s. For the 20 s latch, either report 0xF06F or release it when pct recovers, and use PWM coast rather than brake.

**Merged `jam-latch-single-sample-no-recovery` (confirmed, medium).** The A1 is printing and a brief snag (spool cross-wind, hook-shaped end #99, spool inertia on a fast un-retract/purge) pulls the buffer under 40% for a few ms. The channel latches as jammed and the printer receives 0xF06F, which it shows as a tangled/stuck pause. The BMCU pulls back 10 cm (#127: 'filament was retracted a bit from extruder'). When the user resumes, the printer's send_out is answered with the motor stopped and 0xF06F again, so it pauses again (#127: 'came back to printing and right after that paused it back again'). The workarounds users report match the only clear paths: 'remove all filament and feed it again' (#139, #127, #55) or 'rebooting the printer fixes it', which also reboots the BMCU and clears the RAM latches. Review: The code matches the claim. On our A1 build (SOFT_LOAD=0, P1S=0), the on_use target is 52% with band 51.8..60 (Motion_control.cpp:302-309). Motion_control.cpp:1904-1908 sets both latches the first time MC_PULL_pct_f < 40, with no time qualification. The ADC window is ~4.8 ms: 8 ch x 84 cycles at PCLK2/8 = 18 MHz, x32 x4 blocks (ADC_DMA.cpp:245, 303). Once latched, three things keep it latched. (a) set_motion() does not clear low_latch while jam_latch is set (789-793). (b) The on_use path returns with PWM 0 while low_latch is set (1025-1033). (c) Motion_control_run re-forces A.pressure=0xF06F every loop for on_use and send_out, after MC_PULL_ONLINE_read has recomputed pressure (2767-2777). There are only three clear paths. MC_ONLINE_key_stu==0 (2757-2761), pct>85 while the printer is in send_out (2246-2252), or a reboot. The idle case also keeps the motor stopped (2355-2360). Upstream #127 describes exactly this: an A1 with a red LED that pauses again after resume, fixed only by removing the filament or rebooting. The 'no recovery after the snag clears' half is clearly a defect. The V10 changelog calls immediate detection intentional, but V9 used to auto-release at neutral and that was removed. I lowered severity for our setup because the buffer is a mechanical integrator. Going from 52% to 40% needs real filament displacement, and with a 0.2 mm nozzle the extrusion rate is very low. A true trip therefore needs a feed stall of seconds, not 'a few ms'. False trips are less likely on our machine, though a genuine brief snag still leaves the print stuck. Corrections: The '~5 ms / single reading' framing overstates the risk: the ADC window does not limit how fast the buffer can physically move, the extrusion rate does. On a 0.2 mm nozzle a trip needs a multi-second stall. Keep the debounce but make auto-clear the main fix: release jam_latch after pct is back at or above target-delta (~51.8%) for about 1 s, or when the printer issues before_on_use/on_use for the channel. Add the missing clear-path references: 789-793 (set_motion refuses to clear) and 1025-1033 (on_use stays at PWM 0). For SOLO 0.095 the hard-coded 0.100 m pull-back is irrelevant, as the finding says.

<a id="flash-save-same-iteration-as-tx"></a>
### 3. Filament-info and loaded-state flash writes run in the same loop pass that starts the reply, with IRQs off; the TC ISR that releases DE is deferred and RX is blind

- **id:** `flash-save-same-iteration-as-tx` (merged: `flash-ops-irq-masked-hot-path`)
- **kind / severity / A1:** bug / medium / direct
- **verdict:** confirmed
- **status:** fixed on `main` (`e0dbe12`: NVM writes in quiet bus windows, debounced); hardware validation pending
- **location:** src/main.cpp:229-251, src/Flash_saves.cpp:78-93, src/Flash_saves.cpp:63-76, src/Flash_saves.cpp:304-317, src/Flash_saves.cpp:397-414, src/_bus_hardware.cpp:113-131
- **related:** upstream #126 (random failures saving filament info), possibly #127/#139 (errors during load/unload)

**Failure scenario.** The user edits slot 1 on the A1, and the printer sends 0x08 set_filament_info. The BMCU starts the 8-byte ACK and immediately starts programming flash. If this is the slot's 6th save, the fast page erase runs with IRQs off. The TC interrupt at the end of the ACK can't run, so PA12/DE stays in TX: the BMCU keeps driving the RS-485 line after its reply, and idle stays false. Any frame the printer sends in that window (the next poll, or a 0x211 read-back of the slot) is corrupted or thrown away. Same pattern on every filament load/unload: set_motion -> ams_state_set_loaded/unloaded -> Flash_AMS_state_write, while the printer is polling motion status. Even without an erase, each word program with IRQs off is much longer than one 8.8 us byte, so bytes are lost.

**Suggested fix.** Move flash work to a quiet window: after the TX has finished (`bus_port_to_host.idle`), the RX parser is at idx 0 with drop_bytes==0, and more than about 1-2 ms have passed since the last RX byte (timestamp STK_CNTL in the ISR). Debounce filament saves (e.g. write 500-1000 ms after the last set_filament for that slot) so bursts collapse into one journal slot. Never start an erase while a reply is in flight. Also consider removing irq_save around FLASH_ProgramWord/erase (no ISR touches flash; the CPU just stalls on fetch if needed), so the USART ISR can at least release DE between operations.

**Review.** Verified. main.cpp:230-231 builds the reply and starts the DMA TX, then 250-251 run ams_datas_save_run/ams_state_save_run in the same pass. Each word goes through flash_word_prog_std with IRQs off (Flash_saves.cpp:85-90). The SDK FLASH_ProgramWord does two half-word programs, each with a BSY wait, so every IRQ-off window is tens to 100+ us, far longer than one 8.8 us byte. The fast page erase (67-73) also runs with IRQs off. Only the TC branch of USART1_IRQHandler drops DE and sets idle=true (_bus_hardware.cpp:126-130), and RX bytes are discarded while !idle (118). So if the IRQ-off window extends past the end of an 8-byte ACK (~70 us) or a motion reply, DE stays asserted and RX stays blind. The printer's next frame collides with our driver or is dropped, and the RX parser has no resync (finding 5), which makes it worse. Reachable on every filament save (10 words), every 6th save per slot (erase), and every load/unload state write (2 words). Severity is medium, not high: these events are infrequent, and the loss is one or two frames that the printer probably retries.

**Review corrections.** The state journal does not erase on every 32nd record from the start. Flash_AMS_state_write erases only after a failed program attempt, which happens only when the target slot is non-blank, i.e. after the 320-slot journal has wrapped once, at each page boundary. The per-word IRQ-off windows are separate, so TC can be serviced between words: the DE hold is bounded by one word program (or one fast erase), not by the whole 10-word record. Also, during the 119 s 'ahub error' half-period (finding 4) the save functions run on every main-loop pass, not only on packet passes, so the quiet-window/debounce design must gate on its own timer. Removing irq_save around flash ops looks viable: the SDK busy-waits in flash-resident code while BSY is set, so execution continues during programming and the USART ISR could run.

**Merged `flash-ops-irq-masked-hot-path` (plausible, low).** The printer sends before_on_use or on_use and the BMCU replies (DMA transmit starts). The main loop then writes the loaded-channel log and, on a page wrap, erases a page with interrupts disabled. The TC interrupt cannot run, so DE stays asserted after the last byte: the BMCU keeps driving the bus and is deaf (idle=false, receive overrun) for the whole erase. The printer's next command, or its retry, collides or is lost. This produces sporadic load/unload hiccups and, if repeated, a comm drop that (because of the registration latch finding) does not self-heal. Review: The structure is as described:
- main.cpp:230-251 starts the DMA reply (send_package) and then runs ams_datas_save_run and ams_state_save_run in the same iteration.
- Every flash primitive masks interrupts with irq_save_wch (CSR 0x800, bits 0x88).
- Only the USART1 TC handler releases DE and sets idle (_bus_hardware.cpp:122-131).
- RX bytes are dropped while !idle (line 118).

The impact is overstated. A loaded-state write is 2 words, which is 4 half-word programs in FLASH_ProgramWord. That most likely finishes while the 44-62 byte motion reply is still going out (about 390-550 µs at 1.25 Mbaud, 11 bits per character), so TC and DE release are usually not delayed at all.

Only two cases plausibly hold DE and leave RX deaf past the end of the transmit:
- The inline page erase. After the first 320 records this happens once per 32 STA writes, which is about once per 16 filament changes.
- The 10-word filament-info write right after the 8-byte set_filament reply, which is a user action and not part of load/unload.

That is orders of magnitude rarer than the 1 ms WS2812 masking in #134. No measurement exists, and the printer retries lost polls. Corrections: - Correct 'These run in the busiest part of the load/unload handshake'. The word programs overlap with the reply's own transmit time; only page erases and filament-info saves plausibly extend the DE/deaf window.
- Measure first (GPIO toggle around flash256_erase and flash_word_prog_std), then gate NVM work on bus_port_to_host.idle && send_data_len==0.
- On CH32V203 the CPU may stall on flash fetch during an erase anyway. If so, masking makes no difference, and the real fix is RAM-resident (.highcode) ISR code.

### 4. Bus-offline detection is broken on BambuBus-only printers: the AHUB timeout (never seen on A1) alternates error/none every 119 s, and both timeouts wrap, so error=-1 is rarely/briefly set

- **id:** `offline-detect-ahub-bambu-merge` (merged: `offline-error-phase-dependent`)
- **kind / severity / A1:** bug / medium / direct
- **verdict:** confirmed
- **status:** fixed on `main` (`a6a84f6`: latched per-protocol link state); hardware validation pending
- **location:** src/main.cpp:233-258, src/ahub_bus.cpp:358, src/ahub_bus.cpp:407-408, src/bambu_bus_ams.cpp:1273-1288, src/Motion_control.cpp:2519-2527, src/_bus_hardware.cpp:12

<a id="rx-parser-no-resync"></a>
### 5. RX parser has no inter-byte timeout/IDLE resync and ignores PE/FE/ORE, so one lost byte costs two frames and a false sync can blind RX for up to 1280 bytes

- **id:** `rx-parser-no-resync`
- **kind / severity / A1:** robustness / medium / direct
- **verdict:** confirmed
- **status:** fixed on `main` (`5e0f404`: resync on 200 us line gaps and ORE); hardware validation pending
- **location:** src/_bus_hardware.h:61-178, src/_bus_hardware.h:63-68, src/_bus_hardware.h:109-128, src/_bus_hardware.cpp:113-119
- **related:** #126, #141 (intermittent comm loss)

**Failure scenario.** An IRQ-off window (WS2812 or flash, previous findings) drops k bytes of frame A. The parser is still waiting for k more bytes and takes them from the start of frame B, including B's 0x3D header. A then fails CRC16 and B is never seen. Each glitch costs two frames, often the printer's request plus its retry. If the parser then locks onto a 0x3D/0x33 payload byte whose fake header passes CRC8 (1/256), it can swallow up to 1280 bytes (~11 ms) of traffic. The same happens if a heartbeat is being dropped (drop_bytes > 0) when bytes go missing.

**Suggested fix.** In the ISR, record `last = STK_CNTL` per byte. If `(now - last) > ~3-5 byte times` (e.g. 40-60 us, 720-1080 ticks), set `_index = 0; drop_bytes = 0;` before handling the byte. Or enable USART IDLEIE and reset the parser on IDLE. Also reset on PE/FE/NE/ORE, and clear ORE correctly by reading STATR then DATAR. This pairs naturally with moving RX to circular DMA plus IDLE-line framing.

**Review.** Verified. _bus_port_deal::irq (_bus_hardware.h:61-178) leaves a frame only by counting to `length` or on a header CRC8 mismatch. It has no inter-byte timeout, no IDLE-line reset, and no reset on USART error flags. drop_bytes (63-68, 146-152) is also counted blindly. So if k bytes are lost to an IRQ-off window, the next frame's first k bytes (including its 0x3D) complete the broken frame, that frame fails CRC16 in get_packge_type, and the following frame is lost too. A false sync on a 0x3D/0x33 payload byte passes CRC8 with probability ~1/256 and can then swallow up to 255 bytes (short header) or 1280 bytes (long header). This makes every byte-loss source in findings 1 and 3 worse, and it affects our A1.

**Review corrections.** ORE is already cleared implicitly: USART_GetITStatus reads STATR (SDK ch32v20x_usart.c) and USART_ReceiveData then reads DATAR, which is the ORE clear sequence. What is missing is resetting the parser (_index=0, drop_bytes=0) on ORE/FE/PE, on an inter-byte gap, or on IDLE. The inter-byte-gap reset (for example >3-5 byte times, using STK_CNTL in the ISR) or IDLEIE is the right fix.

### 6. pull_back and redetect states have no timeout/stall limit and block all printer motion commands while active

- **id:** `pullback-redetect-unbounded-blocking`
- **kind / severity / A1:** robustness / medium / direct
- **verdict:** confirmed
- **status:** open
- **location:** src/Motion_control.cpp:2122-2199, 1435-1438, 1706-1712, 2519-2523
- **related:** #125 (unload failures), general runaway-motor concern

**Failure scenario.** (a) During an A1 unload the user pulls the filament out of the BMCU, or the channel being unloaded was only partly loaded after a failed feed. **Suggested fix.** Add a hard limit to both states: pull back max time about (target / 12 mm/s) + 2 s; redetect max distance about 30-50 mm (from AS5600) or max time about 2 s. Add stall detection (PWM at least 800 and |speed| < 1 mm/s for more than 0.5 s leads to stop). When a limit is hit, go to idle and let motor_motion_switch run. Also exit early if the printer changes now_filament_num or the channel's motion away from pull_back. Apply the same limits to the unbounded DM states S2_PUSH/S2_RETRACT/S2_FAIL_RETRACT (1175-1316), which also run at 900 PWM with no time or stall bound.

**Review.** The code has no bound on either state. filament_pulling_back (2131-2170) exits only on `d >= target` or ks==0, and refreshes the 100 ms over_time on every loop. filament_redetect (2172-2190) keeps set_motion(redetect) while ks==0. run() sets `x = -dir * 900.0f` (1437) and writes the PWM directly (redetect early-return about 1798-1804), even when ks==0. While either state is active `wait=true`, so motor_motion_switch is skipped for all channels (2521-2522). Printer commands update A.filament[].motion but are ignored. online is forced true (2832-2833). Reachability for our A1: the redetect-forever case needs ks==0 after the pull back, which in practice means the user pulled the filament out of the BMCU mid-unload. **Review corrections.** (1) The 'partly loaded after a failed feed' path to ks==0 is doubtful. ### 24. send_package starts TX without checking for an RX frame in progress or reply age; parser state is not reset around our TX

- **id:** `tx-no-collision-guard`
- **kind / severity / A1:** robustness / low / direct
- **verdict:** plausible
- **status:** open
- **location:** src/_bus_hardware.h:180-193, src/_bus_hardware.cpp:91-110, src/_bus_hardware.cpp:118, src/bambu_bus_ams.cpp:1262, src/main.cpp:229-231
- **related:** #141

**Failure scenario.** The main loop is held up (e.g. flash erase from the previous finding, or several strips dirty) past the printer's reply window. The printer moves on and starts its next frame (a heartbeat or a poll for another address). The BMCU then raises DE and transmits the stale reply on top of it: both frames are destroyed. Afterwards the parser, which kept its partial state, eats the start of the following frame too.

**Suggested fix.** Timestamp frame completion in the ISR (store STK_CNTL next to recv_data_len). In send_package, skip or drop the reply if `_index != 0 || drop_bytes != 0` or if its age is over a limit (to be tuned from a bus capture, e.g. 1-2 ms). Add a `rx_reset()` method and call it at TX start and in the TC branch. Longer term, handle and answer packets outside the heavy parts of Motion_control_run (e.g. call bambubus_run/send_package between the AS5600 transaction and the PID step).

**Review.** The code facts hold. send_package (_bus_hardware.h:180-193) checks only `idle`, not `_index`/`drop_bytes`. RX bytes are discarded during TX (_bus_hardware.cpp:118) while the parser's partial state is kept. The reply is sent after processing at the start of the next loop pass plus delay_us(50) (bambu_bus_ams.cpp:1262). The failure needs the loop latency to exceed the printer's reply timeout, and nothing establishes that. The worst normal pass is roughly the AS5600 soft-I2C burst (4 us half-bit delays, a few hundred us, gated to once per ms) plus one dirty strip (~160 us including the 100 us RST with IRQs on) plus the ADC work, so under 1 ms. Flash operations run after send_package, so they delay the next reply, not the current one, and during them RX is blind anyway. In normal master/slave polling _index is 0 when we transmit, because the printer waits for our reply.

**Review corrections.** The latency is up to the remainder of one pass (plus about 50 us), not a full pass. The flash-erase example does not make the current reply late, because the erase starts after send_package. A cheap rx_reset() at TX start and in the TC branch is still a sensible hardening, and it pairs with the resync fix in finding 5. Any reply-age limit should come from a bus capture.

### 26. SOLO pull-back length is nondeterministically shortened by a before_pull_back accumulator whose direction lock needs >0.5 mm of motion in a single ~1 ms loop

- **id:** `before-pullback-retract-nondeterministic`

**Review.** This is right as a configuration fact. SetSysClockTo144_HSI in the SDK sets HPRE /1 and PPRE2 /1, so PCLK2 is 144 MHz, and `RCC_ADCCLKConfig(RCC_PCLK2_Div8)` (ADC_DMA.cpp:245) gives an 18 MHz ADCCLK. That is above the 14 MHz ADCCLK limit in the CH32V20x RM/datasheet, which is inherited from the STM32F1 ADC. I could not find the limit in the local SDK sources, so verify it against the datasheet. RegSimult mode with ADC1 and ADC2 configured for the same channel in the same rank (280-305) is the pattern the STM32F1 RM forbids (overlapping sampling of one channel). The practical effect is undemonstrated. Each published value is a sum of 4×32×2 = 256 conversions, the Hall outputs are low-impedance, and 71.5-cycle sampling leaves plenty of settling time, so expect a small INL/offset shift rather than gross errors. It is only relevant because of the tight thresholds in the other findings.

**Review corrections.** Keep it low priority. The simplest compliant change is RCC_PCLK2_Div16 (9 MHz). That halves the scan rate: the filter window grows from about 4.8 ms to about 9.6 ms, and the calibration and jam timing assumptions should be rechecked. Changing APB2 to /2 is also possible, but it affects USART1 and the timer clocks, so it is more invasive. Offsetting ADC2's channel order would need the de-interleave in process_half_update_filter rewritten.

Gaps the completeness critic listed but did not check:

- CHECKED BY THIS CRITIC, NO DEFECT FOUND (so these are no longer gaps). (a) Stack: the largest frames in our variant's image are nvm256_write at 256 B, MC_PULL_calibration_boot at 224 B, motor_motion_run at 160 B, main at 128 B, plus the 64 B -msave-restore helpers. The worst call chain is under about 1 KB against the fixed 2 KB stack. There is also 7,120 B of unused RAM between _ebss (0x20002C30) and the stack bottom (0x20004800), so an overflow would land in unused RAM before touching .bss. (b) hal/time_hw.c: the 64-bit SysTick read uses a correct hi/lo/hi retry, the delay and ms/us conversions saturate, and every 32-bit tick comparison outside main/ahub uses unsigned differences with windows of 30 s or less. (c) The startup code sets INTSYSCR=0x3 (HPE plus nesting), so the WCH-Interrupt-fast USART1 ISR is valid. USART1 is the only IRQ enabled at runtime; the USART3 ISR is compiled in but never enabled with Debug off. (d) Data shared between the ISR and main is read under irq_save_wch, which has a 'memory' clobber, so it is safe under LTO. (e) The hardware CRC unit is used only from main context, and its clock is enabled in Flash_saves_init before the first NVM read. (f) ADC DMA: the polled half/full-buffer processing reads whole 32-bit words, so a late poll only mixes samples of different ages and never produces torn values. (g) WS2812 bit timing is within the datasheet: T0H 389 ns, T1H 833 ns, bit period 1.222 us. All GPIO writes from the ws2812 code, the DE pin and the soft-I2C use BSHR/BCR, so they cannot race the ISR through read-modify-write. (h) The image contains no compiler-inserted ebreak/unimp traps (the unimp hits in the disassembly are rodata). (i) Calling SystemInit twice (startup, then main) is harmless.
- NOTE ON AN EXISTING FINDING (calibration-timeout-silently-saved, MC_PULL_calibration.cpp:272-284). On timeout, both capture functions return center_v. If BOTH extremes time out, `if (vmax <= vmin + 0.10f)` is always true: a host float simulation over centers from 1.40 to 1.90 V widened 715 of 715 cases. The result is saved as center ±0.10 V, so the jam threshold (40%) sits about 20 mV below rest. The ±50 mV range, which puts the jam threshold about 10 mV below rest, only happens when exactly one side times out. Both cases are hypersensitive, so the finding stands, but its numbers should say which case they describe.
- Power loss during a flash write. flash256_prog (Flash_saves.cpp:51-58) erases the page before programming it, and a full journal page is erased before the new slot is appended. Power loss in that window of a few ms loses the record entirely, rather than leaving a torn record that the CRC would catch. The fallback would be default PETG, or no loaded channel. PVD is not used. Writes normally happen only while the printer is powered and sending commands, so this is low likelihood; the persistence area should confirm the fallback behaviour.
- UART timing depends entirely on the HSI oscillator. The board has no crystal: PD0/PD1 are remapped to GPIO, used for the AS5600 SDA on channel 0 and for SYS_RGB. BRR = 144 MHz / (16 x 1.25 Mbaud) = 7.2, programmed as 7.1875, which gives a +0.17% baud error. I did not check the CH32V203 HSI tolerance over temperature against the roughly ±3% receiver tolerance for 11-bit frames. Measuring the actual baud rate with a logic analyzer on our unit would settle it.
- I did not check whether the CH32V203 reference manual constrains fast page erase/program (FLASH_ErasePage_Fast / FLASH_ProgramPage_Fast) at SYSCLK = 144 MHz, for example a required HCLK division. Saves work in the field, so this is low priority.
- Recalibration gesture false trigger (Motion_control.cpp:2785-2821). When all_no_filament() is true, holding any inserted buffer 'hard_blue' for 5 s (pct <= 15, or v <= 1.55 V, or v <= MC_PULL_V_MIN + 0.03) wipes the entire NVM and reboots. With a timed-out calibration that threshold is only 20-70 mV below rest. I did not evaluate this against real Hall-sensor drift or a buffer resting slightly off-center with no filament.
- Auto-unload gesture (Motion_control.cpp:2537-2640): pct >= 80 followed by 45-55% within 1 s pulls at 850 PWM for up to 15 s. manual_empty_pull (key==0 && pct>80) pulls at 700 PWM with no time limit. Both run whenever the channel's motion is pressure_ctrl_idle, including right after a printer-commanded pull_back or redetect. I did not analyze whether the A1 SOLO unload sequence can trip them.
- DE (PA12) and TX (PA9) stay floating inputs from reset until bus_init() at the end of boot. That is about 0.6 s on a normal boot, but minutes during first-boot calibration, and every BMCU Flasher reflash erases NVM and forces that calibration. Whether the 370C board has a pull-down on DE, which would keep the transceiver from driving the bus in the meantime, needs the schematic.
- PC13-PC15 are used as AS5600 SDA in 50 MHz open-drain mode. These are backup-domain pins with limited drive and speed on STM32F1-class parts. I did not check the CH32V203 limits or scope the I2C signal integrity; this is relevant to the AS5600 read-failure finding.
- The main-loop period and reply latency have never been measured. Adding a max-loop-time counter and a late-reply counter, shown via LED or debug output, would validate the bus-timing assumptions: about 1 ms per loop, AS5600 reads at about 0.45 ms, and the late-reply risk.
- Debug builds: with Debug_log_on defined, Debug_log_write_num busy-waits on TC in the main loop (about 87 us per byte at 115200 8E1). That would break BambuBus timing, so debug builds are not representative for timing-sensitive tests.
- ahub_bus.cpp was only reviewed for its timeout. On the A1, a false 0x33 frame needs both CRC8 and CRC16 to match, which is negligible, but I did not audit whether the AHUB reply path could ever transmit onto the BambuBus.
- bambu_bus_ams.cpp reply constants (before_on_use_sniff rows, unknow3/last1/last2, the 0xFF74 idle pressure, the online_detect prefixes) were not checked against what A1 01.08.01.00 expects. The protocol semantics are unverified, and a live capture would be needed.
- RCC reset-cause flags (RSTSCKR: watchdog, low-voltage, software, pin) are never read. Recording them would help diagnose field reports like #148, #141 and #126 where a BMCU reset changes the behaviour.
