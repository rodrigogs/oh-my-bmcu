# oh-my-bmcu

A fork of [jarczakpawel/BMCU-C-PJARCZAK](https://github.com/jarczakpawel/BMCU-C-PJARCZAK) maintained for one concrete setup: a single BMCU 370C on a Bambu Lab A1. Every change lands with an adversarial code review, a green CI and host unit tests for the logic that can be isolated from the hardware, and stays easy to send back upstream. Validation on the A1 itself is tracked in the [hardware test plan](hardware-test-plan.md), with results in the [hardware test log](hardware-test-log.md): until an image has passed it, treat it as untested on hardware. Run 1 exercised the image of `cec0e00`, and Run 2 smoke-tested the image of `68c77c6` (the same as `cb1d94d`'s, the last before the V11 merge). Since the merge of upstream V11 (`5b8e235`, merged on 2026-10-14) the bus, the flash writes, the calibration and some LEDs work differently, and no merged image has run on the A1 yet.

## Target setup

| | |
|---|---|
| Printer | Bambu Lab A1 (model code N2S), printer firmware 01.08.01.00, AMS type set to **AMS** (not AMS Lite) |
| BMCU | one BMCU 370C with Hall sensors |
| Firmware variant | `standard(A1)` load force, AMS_A (`BAMBU_BUS_AMS_NUM=0`) with 0.095 m retract, AUTOLOAD, filament RGB off, on upstream V11 |
| PlatformIO env | `a1_solo_autoload_rgboff` (the default env) |
| Slicer | [OrcaStudio](https://github.com/jarczakpawel/OrcaStudio): on A1 firmware 01.08.x it ignores the blocking print error `0500-409D` and retries the print |

## Differences from upstream

Upstream here is V11 (`5b8e235`). Findings and their status are in the [audit backlog](audit-2026-09.md), the list of commits in the [changelog](CHANGELOG.md). In short:

**Taken from V11.** Where V11's rework covers a fork fix, the merge takes V11's code: RX through a 2 KB DMA ring that `bus_rx_poll()` parses in the main loop (no per-byte RX interrupt, so no byte is lost while interrupts are off), a queue that keeps up to two received frames while a reply is pending, TX by DMA with the receiver off and a 100 ms abort, flash writes as background jobs (one page erase or one half-word program per main-loop pass, started only while `bus_background_ready()`, and a sticky fault with no retry after a failed step), filament records that roll a full page over through a scratch page the boot replays after a power loss, a loaded-channel log that never erases the page holding its newest record, the CAL v2 record (DM key thresholds, a per-channel valid mask, two pages with a sequence number), the fail-closed calibration, V11's `MOTOR_get_dir` direction test, the int64 AS5600 odometer, calibration averages in float, and AMS_AUTO addressing (compiled in CI through `env:moj`, not used by the default env). This drops the fork's interrupt-driven RX parser with its overrun resync, the NVM writes in quiet bus windows with their 500 ms debounce and retry back-off, the calibration fallback range, the fork's direction probe and `host_link_offline()`.

**Bus with the printer**
- LED strips: the 10 ms throttle of upstream PR [#134](https://github.com/jarczakpawel/BMCU-C-PJARCZAK/pull/134) (Murilo Bastos), verified on the A1 on 2026-09-23, and a redraw only when a strip's colour actually changes (V11 redraws the active strip every 1 ms whenever the bus is idle, with interrupts off for about 59 us per strip). Like V11, nothing is drawn while the bus is busy or while the flash clock is slowed for a flash step; the change stays pending and does not use up the 10 ms gap.
- A frame that lost bytes or began on a false header is dropped once `bus_rx_poll()` has seen no new byte for 200 us (V11 waits 11.3 ms, which never happens while the printer keeps polling, so a false header could swallow up to 1,280 bytes). The time is measured between polls, from the poll that first saw the last byte, so in practice it is 200 us plus up to about two main-loop passes: a printer frame that starts sooner can still be lost (one request, which the printer retries).
- A frame our own reply cut (we answered while the printer was already sending) is dropped at the ring position where our TX started, so its head cannot combine with the bytes after the TX; this also holds when the cut frame is a heartbeat that V11's fast path would skip in one step. V11 resets nothing around its TX.
- A lost printer link is latched (V11's check still depends on a 119 s timer phase), so the motors stop within about 1 s of the printer going silent.
- In fixed addressing (AMS_A to AMS_D) AMS discovery is answered again after a link loss. In AMS_AUTO the fork keeps V11's rule, since a re-arm there picks a new token and would leave the unit deaf until the printer reran discovery.
- Frame-length checks are V11's: 0x03 12, 0x04 13, 0x05 8 (26 for the confirm), and set-filament 0x08 45 bytes and 0x218 34 data bytes (the fork had 11, 12, 25 and 18). A set-filament frame is saved only when its data was applied to this unit (V11 also saves a slot when the unit is offline, data it did not apply). The A1's set-filament frame length was never captured: if slot edits from OrcaStudio stop applying, the fork's shorter minima come back as a follow-up.
- AHUB (the 0x33 protocol of other printers; the A1 only speaks BambuBus): V11 applies a set request only if its data lies inside the frame and drops one that names a channel other than 0-3 or none; the fork also drops frames without the short header, which V11 still accepts when the two length bytes agree.

**Motor and sensors**
- Tangle detection: the buffer must stay below 40% for 500 ms while the BMCU pushes at full force before the print pauses (V11 still trips on a single reading). The latch is meant to release when the printer resumes the channel after the buffer has been above 40% at least once (free the spool, feed filament, resume), or when the buffer is held at or above about 52% for 1 s while printing or paused. Since V11 a before_on_use counts as a resume only after a send_out, so a paused print is resumed, and released, by on_use. 52% is only a few mV above the buffer's rest position, inside its rest scatter, so a buffer that rests slightly high can release the latch by itself; a resume then pauses again 0.5 s after the buffer drops below 40%. Which commands the A1 sends on a resume has not been observed yet, so this is still to be confirmed on the printer. Full-force pushing is still capped at 20 s of push time, at any buffer level (the anti-stall's 0.5 s rests pause the count, so a stalled gear brakes after about 32 s). While latched, the BMCU does not push the channel, whatever the printer commands next: before_on_use and the idle control (once another channel or none is active) are braked, and unloads still only retract. Lifting a latched channel's buffer never starts the auto-unload: held at or above 85% for 1 s it releases the latch, and letting go afterwards does nothing, also if the buffer sagged (without reaching the middle) and was lifted again while held. Once the buffer is back in the middle of its travel (below 55%), a new lift unloads as usual; if it stops above that when let go, press it down to the middle once first.
- Unload pull back, redetect and the DM autoload Stage-2 have time, distance and stall limits (V11 bounds only its autoload fail retracts). A pull that stalls (for example filament still held by the extruder) stops after about 1.6 s, and that channel's LED blinks red (1 s on, 1 s off) until the filament is pulled out or the slot is used again. The pull back ends on empty switches once 5 fresh ADC publications in a row have read them empty (V11, a few ms). A printer pull back on a channel without a valid calibration, whose motor cannot drive, ends at once with the same red blink, instead of waiting out its 9.9 s budget while every channel's printer commands wait.
- The load (the printer's send_out) stops on a gear that does not turn: 800 PWM or more with less than 1 mm of travel in 1 s ends it, about 1.7 s after it starts, or 1 s after the gear stops if it was feeding. V11's 10 m cap stays, now in the same limit. The channel stays braked until the printer's next command for it. No LED changes: the printer's own load timeout reports it. So a snag that holds the gear for 1 s at full force now ends the whole load.
- The buffer-lift auto-unload (850 PWM, up to 15 s) stops after 1 s on a gear that does not turn, and the channel's LED then blinks red as after a stalled pull back. Its 15 s end sets no fault. The manual empty pull (700 PWM, no filament at the switches, buffer held up) has no stall limit. Neither runs on a channel without a valid calibration (its PWM is held at 0) nor, with the DM board, while its autoload fail latch is set (V11).
- The idle control's push (a parked or idle channel with the buffer below 30%, about 510 to 800 PWM; the 420 PWM hold floor is the stall level) is braked after 1 s with the gear stalled (420 PWM or more, less than 1 mm) or after 10 s of pushing. At a rounded 28-29% the brake is silent (a gear that stops just short of 30%); below 28% the status LED turns steady red. The brake ends when the buffer is back at 30% or above, when the printer moves the channel, or when no filament is at the switches; if the buffer falls to a rounded 26% or less during a silent brake, a new push starts (a one-point dip to 27% keeps the brake, so ADC noise does not push a stopped gear again). A steady red (this fault, or a failed DM autoload) hides the unload-fault blink on the same channel until its next move.
- If the ADC readings stop coming for more than 100 ms (the buffer and filament-switch voltages would be frozen), every motor is braked, a running auto-unload ends, the tangle latch neither trips nor releases (also not through the load's release above 85%) and its 500 ms trip and 1 s release timers start again from the first fresh reading, the 5 s recalibration hold starts again from the first fresh reading, and every channel's status LED blinks pure blue (250 ms on, 250 ms off, all four together; a channel with an AS5600 fault stays steady red instead) with the buffer LEDs off. The brake does not change what the channel was doing, so a channel braked by the 20 s full-force limit, a load stopped by its stall limit and an idle push braked by its limit are still braked once the readings are back (a printer command for the channel during the stop still ends them as usual), and a load or unload does not replay its soft start. Everything resumes from the first new reading. The printer keeps getting the last filament state and pressure. While the readings are stale the ADCs and the DMA are restarted every 500 ms, and right after a DMA transfer error (V11 leaves the stream dead until a reboot); the readings keep their last values until the first new one. Each ADC's two calibration waits (four in all, at boot and at every restart) give up after 10 ms each instead of hanging the boot at the dim red SYS LED; a timeout sets `g_adc_cal_timed_out`, readable only with a WCH-Link. If the ADC delivers nothing at boot, the blue blink shows from the first pass and no restart is tried.
- V11's AS5600 driver reports which reads are valid and keeps the last angle on a failed one; the fork's tracker also skips implausible jumps. The motor-direction test is V11's: a still baseline, then 1000 PWM until the angle has moved more than 163 counts, then two reads that confirm the direction before it is saved, up to 200 steps of 10 ms, each with a watchdog feed. It runs at boot only on a channel whose direction is unknown, whose AS5600 works, whose buffer has a valid calibration and whose switches are empty, so a channel with filament at its switches at the first boot after a flash keeps no direction and does not drive until a boot with its switches empty.
- Every motion distance (unload length, autoload Stage-2) comes from V11's integer AS5600 odometer, as a difference of its low 32 bits, so unloads stay 95 mm at any odometer value. V11 still shortened the pull back by a before_pull_back accumulator whose direction lock needs more than 0.5 mm in one pass; the fork always pulls the configured length.
- DM autoload only re-arms its 120 mm Stage-2 push after the filament really left both switches or was retracted, not after a switch flickers, and Stage-1 is closed while the printer or an auto-unload moves the channel and until the filament counts as out with the channel idle (V11's gate, with the fork's re-arm). A flickering switch no longer restarts the push either: the remaining length, the abort count and the time and stall limits carry over, so with the printer link up a gear that cannot turn gets at most about 6 s of push per insertion, whatever the buffer or buffer-lift unloads do. A failed autoload then retracts at 900 PWM (V11): up to 1.5 s after a Stage-1 timeout, or after the third buffer abort up to 1.5 s plus 1.5 s more while the key reads 'external only', at most 120 mm. A free gear so pulls the filament out and the channel re-arms; a jammed one stays red with the motor off. A time or stall limit fails the run at once, with no retract. An insertion ends only after both switches have read empty for 100 ms: a shorter glitch stops the drive while it lasts, then Stage-1 or Stage-2 goes on where it was, so a loose key wire no longer restarts the 5 s Stage-1 push or a new 120 mm Stage-2. A failed channel stays red through such a glitch, and its red (and the buffer-press gesture's lock-out) ends up to 100 ms after the filament is pulled out. Key readings more than 20 ms old (a stopped ADC stream) do not count: the 100 ms starts again from the first fresh reading, so a stream that stops right on a glitch no longer unloads a loaded channel and pushes it another 120 mm once the readings are back. The printer still sees the switches' raw state at once.
- While the printer link is down (SYS LED red), lifting the buffer no longer drives the motor: the auto-unload and the empty-channel pull only run with the link up.

**Calibration and flash**
- The calibration is V11's and fail-closed: a step that times out (30 s), a reading outside 0.05 to 3.25 V, or a range narrower than V11's minimum (50 mV on each side, 120 mV in all) fails the whole run. Nothing is saved, every buffer LED blinks dim red twice (220 ms on, 220 ms off), every buffer stays without drive until a calibration succeeds, and the next boot calibrates again. The fork adds a floor: a first step whose end lies less than 190 mV below the idle centre fails the run too, and a stored record with a narrower low side is calibrated again. V11 keeps any step past 100 mV, which put the tangle latch 20 mV below rest, inside the 25 mV the calibration itself accepts as back at rest.
- The 5 s recalibration hold clears only the calibration and motion records (V11), so the filament slots and the loaded channel are kept. It skips a buffer without a valid calibration (fork): such a buffer reads its raw voltage, and one idling at 1.55 V or less fired the hold 5 s after every boot, a clear-and-reboot loop with two flash erases each time. That buffer calibrates again at every boot anyway.
- Flash writes are V11's background jobs, started only while the bus is idle, with no debounce and also while the printer link is down. A filament record is 10 words programmed one half-word per pass; a slot's page holds six records, and the record after a full page (the seventh after a flash) rolls the page over through the scratch page (3 erases), and a power cut at any step leaves the old or the new record. A failed step sets a sticky fault that stops every NVM write until the next boot, readable only with a debugger (`g_flash_fault`).
- A journal slot is programmed only if it reads exactly erased (`0xE339E339`). V11 also takes `0xFFFFFFFF` as free, and programming over such a word (an older 0xFF-padded layout, a non-erasing programmer) fails its read-back and sets the sticky fault at every boot. The loaded-channel records now carry V11's tag `0xA6`, so a record written by a pre-merge image is ignored (BMCU-Flasher erases the whole NVM anyway).

**Watchdog and faults**
- An independent watchdog (1 s nominal, 0.67 to 1.6 s over the LSI tolerance) resets the BMCU if the firmware hangs; V11 has none. It starts after the first-boot calibration. After a watchdog reset the SYS LED flashes magenta three times at boot. The boot's channel detection feeds it before each of its 16 ADC samples, so ADC restarts there (a DMA transfer error on every read with a stuck calibration bit, about 42 ms each) cannot add up to a reset at every boot. V11's direction test is fed at each of its 10 ms steps and the recalibration after each of its two flash steps, so every path stays under the 100 ms feed gap (worst: about 83 ms, the recalibration with a failing erase).
- A CPU trap (illegal instruction, bad memory access) brakes all motors and releases the bus at once, then the watchdog resets the chip; V11 leaves the motors at their last PWM until the printer is power-cycled. After such a reset one blue flash follows the three magenta ones (490 ms instead of 420 ms), so the LED tells a trap from a hang.
- A fault record in the chip's backup registers survives resets: the reset flags that started the run, the resets in a row since the last power-on, what the main loop was doing (its phase, now including V11's background flash step as phase 12, FLASH), its longest pass, and for a trap mepc and mcause. The RX parser also runs inside the NVM, FLASH and RGB phases (`bus_background_ready()` calls it), so a hang there can be the parser. The LED shows only hang or trap; the rest needs a WCH-Link (`mdw 0x40006c04 10` reads the live record, one register per 32-bit word with the low 16 bits valid; `g_blackbox_last` in RAM holds the run before the reset). A trap before the record is set up (startup code, SystemInit, the clock setup) is not recorded. The boot clears the record's magic first and writes it last, so a reset during that write leaves no record (the count of resets in a row starts again at 1), never an earlier run's trap. The board probably ties VBAT to VDD, so a power cycle likely clears the record (unconfirmed). The ADC calibration timeout and V11's sticky flash fault are not in the record (all 10 registers are used); a debugger reads them in RAM (`g_adc_cal_timed_out`, `g_flash_fault`).

**Upstream #148 (A1 no longer finds the AMS after a power cycle with a channel loaded)**
- The cause is unproven. Upstream closed #148 with V11 without the reporter's confirmation. At boot V11 unloads a restored channel whose switches read empty or whose calibration is not valid, but a present loaded channel is still reported in use from boot. The fork also resets a restored channel to idle as soon as its switches read empty later on.
- `env:a1_solo_autoload_rgboff_no_boot_restore` (`-DBMCU_BOOT_RESTORE_LOADED=0`) is an A/B image that boots every channel idle and applies the restored state only when the printer first references the channel. See the A/B procedure in the [hardware test plan](hardware-test-plan.md#6-upstream-148-ab-test).

**LEDs added by V11**
- A connected buffer without a valid calibration shows a steady dim red buffer LED (its motor does not drive), so a steady red now also means "not calibrated", next to the fork's steady-red faults below.
- The mid-buffer orange (the buffer at its calibrated centre, 49-51%) shows only when every channel is empty.
- The SYS LED is red while the printer link is down (and in AMS_AUTO while the printer rearranges the units, which never happens with AMS_A) and white on every other pass.

**Tooling**
- Pinned platform and SDK revisions, an explicit env for our variant, validation of the `env:fw` environment variables, a fixed `build_all_firmwares.sh`, host unit tests (`test/`), and CI.
- `src/` builds with `-Wall -Wextra -Wundef -Werror`; `pio check` (cppcheck) runs in CI and fails on any high or medium finding; the host tests also run under ASan and UBSan (`env:native_asan`); CI compiles `env:moj` (AMS_AUTO) and three `env:fw` variants (soft load, P1S, filament RGB with AMS_AUTO, the largest published image) besides the two A1 images, rebuilds 24 V11 images against upstream's manifest, gates the image size at 58 KiB and the free RAM at 2 KiB, pins every GitHub action to a commit, and stops any job after 20 minutes.
- The host tests include golden frames of the BambuBus replies (the real `bambu_bus_ams.cpp` compiled on the host), a fuzz of V11's RX parser with our TX mark, models of V11's flash jobs with a power cut at every step, the calibration floor and record check, the offline decision, the fault record and every motion limit. The test models of firmware code are locked to a hash of the `src/` code they model, and the guard scripts have their own tests.

## Build

```sh
pip install platformio==6.1.19
pio run                      # builds env:a1_solo_autoload_rgboff
ls .pio/build/a1_solo_autoload_rgboff/firmware.bin
```

`src/` is compiled with `-Wall -Wextra -Wundef -Werror`, so a new warning fails the build. Static analysis with cppcheck, over `src/` only (CI fails on a high or medium finding; the low ones are listed in its summary):

```sh
pio check -e a1_solo_autoload_rgboff --fail-on-defect=high --fail-on-defect=medium
```

Host unit tests for the logic that can run off the hardware (Unity, `test/`). `scripts/check_test_copies.py` checks that the firmware code copied verbatim into tests still matches `src/`, that no test redefines a `src/` constant or macro, and that every `test_*` case is passed to `RUN_TEST()`:

```sh
python3 scripts/check_test_copies.py
python3 -m unittest discover -s scripts/tests   # the guard scripts' own fixtures, standard library only
bash scripts/test_build_all_firmwares.sh   # build_all_firmwares.sh OUT_DIR guards, stub pio
pio test -e native           # CI runs the same checks with GCC on Linux
pio test -e native_asan      # the same suites with ASan and UBSan
```

- `env:native` builds with `-ffp-contract=off` (no fused multiply-add), so an arm64 Mac computes the same float results as the x86_64 CI runner.
- A test model marked `adapted from` with `// ---- anchor: <symbol>[ from /<regex>/][ to /<regex>/] ----` lines under it (for example `// ---- anchor: motor_motion_switch ----`) is locked to a sha256 of the `src/` region it names, in `test/adapted.lock`. When a commit changes such a region, the check fails and names the harnesses that model it: review them against the new code, then re-lock with `python3 scripts/check_test_copies.py --relock`. A marker without an anchor is accepted and counted as unlocked; add an anchor to every new one. `Motion_control_run` and `motor_motion_switch` are locked whole, so most edits there need a review and a re-lock; the calls that feed the send, idle push, pull back and redetect guards are locked too. A lock only says the models were looked at, not that they are right.
- The `test/` root holds shared headers only (`bus_rx_frames.h`): PlatformIO puts `test/` on every suite's include path, and a `.c` or `.cpp` there would be built into every suite.

Other variants:

- `env:fw` reads the variant from environment variables. They are validated before compiling (`scripts/check_fw_env.py`):
  `BMCU_DM_TWO_MICROSWITCH`, `BMCU_ONLINE_LED_FILAMENT_RGB`, `DBMCU_P1S`, `BMCU_SOFT_LOAD` (0/1), `BAMBU_BUS_AMS_NUM` (0-3 for AMS A-D, 4 for AMS_AUTO) and `AMS_RETRACT_LEN` (metres, e.g. `0.095f`). CI compiles `env:moj` and three `env:fw` variants, each with one of `BMCU_SOFT_LOAD`, `DBMCU_P1S` and `BMCU_ONLINE_LED_FILAMENT_RGB` at 1 (the last one with `BAMBU_BUS_AMS_NUM=4`), as the last step of its A1 job: an `env:fw` build with other variables makes PlatformIO delete the whole `.pio/build/` tree, so run it after anything that reads the A1 images there.
- `./build_all_firmwares.sh` builds the whole published matrix (1,020 images) into `build/firmwares/`. `OUT_DIR` overrides the output dir and is replaced as a whole: the script refuses one that is the checkout, `$HOME` or a directory above either, and, unless `FORCE=1`, one that exists and is neither empty nor an earlier output of the script (its `manifest.txt` starts with the script's header). `BUILD_ONLY_MIN=1` builds only the 24 images that replace V10.5's SOLO folder: `AMS_AUTO/ams_auto_0.095f.bin` and `AMS_A/ams_a_0.095f.bin` for every mode, AUTOLOAD and RGB combination. `BUILD_ONLY_SOLO`, set to any value, stops the script with an error, so a stale invocation cannot start the full build.
  - `OUT_DIR=firmwares` regenerates the upstream mirror in place (`BUILD_ONLY_MIN=1` refuses it however it is spelled or reached, and any directory that contains it, such as `.`). Only do that with upstream sources. The script replaces the whole directory and writes only the `which_to_choose.txt` guides, so the 22 hand-written `README.md` guides of the published tree are deleted; `git checkout -- firmwares` restores them.

## Flash

Use the CLI of [BMCU-Flasher](https://github.com/jarczakpawel/BMCU-Flasher) (v1.3). It needs `pip install pyserial`. Its GUI calls the same `flash_firmware()` function.

1. Remove all filament from the BMCU, so that no switch of any channel sees filament: V11's calibration fails if a switch reads filament, and its direction test skips such a channel. Unplug the printer from the wall and disconnect the BMCU from the printer. Then connect the BMCU to the computer over USB-C. It shows up as a CH340, `1a86:7523`.
2. From the oh-my-bmcu checkout, run:

   ```sh
   python3 /path/to/BMCU-Flasher/bmcu_flasher.py "$PWD/.pio/build/a1_solo_autoload_rgboff/firmware.bin" --mode usb --verify-last
   ```

   The port is picked by VID/PID. Every block is read back after programming. Without `--verify-last` the CLI skips the last block; the GUI always checks it.
3. Flashing erases all 64 KB, including the NVM sector: calibration, motor direction, filament info and the loaded channel. The flasher then resets the MCU (not a watchdog reset: no magenta or blue flash on the SYS LED), and it boots straight into V11's first-boot calibration, even on USB power (see upstream's [calibration video](https://www.youtube.com/watch?v=Hn_DNzSmhuc)):
   - Leave every buffer at rest while its LED blinks yellow (about 1 s): the calibration samples the idle readings and the switches. A buffer that does not hold still fails it, and so does a switch that sees filament, here or in the last step.
   - Then one buffer at a time, waiting up to 30 s per step. While a buffer's LED blinks blue, move it to its low end, the end the extruder pulls it to when the filament is tight (the same end you hold to recalibrate), fully: at least 190 mV past rest, a step shorter than that fails the run. Let it return to rest. Two yellow blinks confirm the step. While it blinks red, lift it to the other end and let it return; two yellow blinks again, and its LED stays yellow. The order matters: the first end becomes the low end, so a calibration done the other way round inverts the buffer.
   - Finally every buffer must rest and every switch read empty for 1.2 s (within 30 s). Two green blinks mean the calibration was saved.
   - Any failure (a step that times out or is too short, a range too narrow, a buffer that does not settle) ends the run at once: all buffer LEDs blink dim red twice, nothing is saved, and every buffer stays without drive (steady dim red buffer LED) until a calibration succeeds. Power-cycle the BMCU to calibrate again. The fork's old fallback range is gone: Run 1's first calibration after the flash hit it, and on this image that run would end in this abort. A calibration that is cut off is not saved and runs again on the next boot.

   So either do the calibration properly, or disconnect right away and do it at the first boot in the printer. After the calibration, the boot runs the direction test (each motor turns briefly) on every channel with empty switches; on USB power alone nothing turns and the test runs again at the next boot.
4. Reconnect the BMCU to the printer only while the printer is unplugged.

To roll back, flash the last hardware-validated image the same way: the image of `cb1d94d` (identical to `68c77c6`'s, Run 2), sha256 `642dfb208ab8c7b7b2e5486d5a54353e74a617c0963fd90a5cd1967b7dea2857` (52,716 bytes), from the CI artifact `oh-my-bmcu-a1-cb1d94d…-push` or rebuilt from `cb1d94d`. The flasher erases the NVM again, so that image calibrates at its first boot too.

To recalibrate later, remove all filament and hold one calibrated buffer pulled for about 5 s. The buffer LEDs blink blue for 3 s and the BMCU reboots into the calibration. This clears only the calibration and the motor direction: every slot's filament type and colour and the loaded channel are kept. It works with the printer link up or down (not while the ADC readings are stale, see below). A buffer without a valid calibration does not start it (it calibrates again at every boot): power-cycle instead. If the clear fails, the buffer LEDs turn dim red and the BMCU does not reboot: every buffer then counts as uncalibrated and drives nothing until the next boot.

LED patterns that mean a fault, besides the calibration's own:

- SYS LED at boot, three magenta flashes (70 ms on, 70 ms off): the watchdog reset the BMCU (a hang, or a CPU trap). One blue flash right after them: the run before that reset ended in a CPU trap. A power-on, the flasher's reset and the recalibration's reboot show neither.
- Every channel's status LED blinking pure blue together (250 ms on, 250 ms off) with the buffer LEDs off, except a channel with an AS5600 fault, which stays steady red: the ADC readings are stale and every motor is braked. The blue blinks of the calibration and of the recalibration hold are on the buffer LEDs, so neither looks like this.
- A channel's status LED steady red: a tangle, a failed DM autoload, an AS5600 fault, the 20 s full-force limit, or an idle push stopped by its 1 s stall or 10 s limit. Blinking red, 1 s on and 1 s off: an unload or buffer-lift auto-unload stopped by its limit, or a printer pull back on a channel without a valid calibration.
- A buffer LED steady dim red: that buffer has no valid calibration and its motor does not drive (V11). Power-cycle the BMCU to calibrate it.

## Notes

- **`firmwares/` is an upstream mirror.** It holds the 1,020 images upstream published for V11 (`5b8e235`), with their guides. It is not built from this fork's sources. BMCU-Flasher's *Online* mode downloads from upstream, not from here. Images built from this fork come from a local `pio run` or from CI: every push that passes the tests, the V11 reproduction and the static analysis uploads `oh-my-bmcu-a1-<commit>-push` with the `.bin` and `.elf` of `a1_solo_autoload_rgboff` and of the #148 A/B image, and the run summary lists their sha256.
- **Printer-facing version.** The BMCU reports V11's AMS version bytes `{0x00, 0x00, 0x00, 0x0B}` + `"AMS08"` from `src/bambu_bus_ams.cpp`, which the printer shows as 11.00.00.00 (10.50.00.00 before the merge). The `version` file (11.00.00.00) now agrees, but the build still does not read it. We follow upstream's bytes on purpose: printers check the reported AMS version (see upstream [#73](https://github.com/jarczakpawel/BMCU-C-PJARCZAK/issues/73) and [#119](https://github.com/jarczakpawel/BMCU-C-PJARCZAK/issues/119), "the ams version is wrong, printer cannot continue"), so the image reports what upstream ships with the same code. The serial number and the discovery bytes are unchanged with AMS_A. To check on the A1: the printer shows `ams/0` 11.00.00.00 `AMS08` and no new HMS code.
- **Addressing.** The default env keeps `BAMBU_BUS_AMS_NUM=0`, AMS_A, the fixed addressing Runs 1 and 2 validated (V11 calls it legacy). AMS_AUTO (4) is V11's recommendation for new installs and is compiled in CI through `env:moj`, but it has not run on this printer: it adds a registration gate on all traffic and an arrange latch that only a reboot clears. It is left to its own change.
- **CI gates changed with the merge.** `IMAGE_BUDGET_BYTES` went from 57,344 to 59,392 B: the A1 image is 59,156 B (236 B left; the A/B image 59,176 B, 216 B left), and the hard upload limit is 61,440 B. `RAM_HEADROOM_FLOOR_BYTES` went from 4,096 to 2,048 B: the measured headroom is 2,524 B, since V11's 2 KB RX DMA ring took most of the old headroom. The ELF check also requires `DMA1_Channel4_IRQHandler` and `DMA1_Channel5_IRQHandler`. The margins are thin: the next feature probably needs size work or another budget change.
- **Follow-ups, not in the merge.** (1) V11's heartbeat fast path in `bus_rx_poll()` can fire inside a frame's payload (it checks neither `receiving()` nor the header CRC8) and lose more than one frame; the merge only stops it at our TX mark. A fix with a host test, and an upstream issue for it, are to do. (2) A `Flash_fault()` accessor for V11's sticky flash fault, which today only a debugger sees (`g_flash_fault`). (3) Audit #29, the 18 MHz ADC clock, is unchanged.
- **Upstream patches.** The fork's three patch branches for upstream (redraw only on change, erase before write, float calibration mean) were not merged upstream. The fork still carries the first; V11's own rework supersedes the other two.
- **License.** Upstream does not declare a license, so this fork does not add one either. Ask upstream before redistributing the firmware.
- The [upstream README](../../README.md), below the fork banner, describes upstream's releases, flashing guide and safety notes. The safety notes apply here too.
